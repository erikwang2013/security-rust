# security-rust

**🌐 [中文 (原文)](../../../README.md)**

Библиотека обнаружения атак, написанная на Rust, охватывающая 32 детекторов в 4 категориях: инъекционные атаки, протокольные атаки, атаки на данные/сериализацию, утечки файлов/чувствительных данных. Ноль внешних зависимостей фреймворков: цепочка детекторов работает только со строками, а три модуля с состоянием (см. ниже) дополняют её.

Питомец проекта — **甲哨 Sentri** ([`pet.svg`](../../pet.svg)): 32 пластины панциря соответствуют 32 детекторам. Сообщает обо всём, не блокирует ничего.

## Идея дизайна

### Почему «обнаружение», а не «блокировка»

Библиотека позиционируется как **чистый сканер ввода** — принимает строку, возвращает структурированный результат обнаружения. Она не привязана ни к какому веб-фреймворку, не разбирает HTTP-запросы/ответы, не выполняет блокировку в реальном времени. Так вы можете встроить её в любой конвейер: движок правил WAF, аудит логов, предварительную проверку API-шлюза, CLI-инструменты сканирования безопасности и т.д. Модули `session`, `throttle` и `score` (см. ниже) идут дальше: они хранят состояние или агрегируют сигналы, но по-прежнему не привязаны ни к одному фреймворку.

### Принципы архитектуры

- **Единая ответственность** — каждый детектор отвечает только за один тип атаки и внутри хранит скомпилированные наборы регулярных выражений
- **Единый интерфейс** — trait `Detector` — единственный контракт для всех детекторов: `fn detect(&self, input: &str) -> Option<DetectionResult>`
- **Покрытие по умолчанию** — `Scanner::default()` одним вызовом собирает все 32 детекторов, готов к использованию без настройки
- **Опциональная настройка** — `Scanner::builder()` поддерживает настройку по требованию: выборочная сборка детекторов через `.with_detector()`

### Компромиссы

| Решение | Выбор | Причина |
|---------|-------|---------|
| Регулярные выражения vs парсер | Регулярные выражения | В сценариях обнаружения скорость важнее; регулярные выражения лучше покрывают обфусцированные/обходимые паттерны |
| Первое совпадение vs полное сканирование | Полное сканирование | Один ввод может одновременно запускать несколько атак; нельзя допускать пропуск |
| Ноль зависимостей vs подключение serde | Ноль зависимостей | Зависит только от `regex` — быстрая компиляция, малый размер |
| Детекторы vs модули с состоянием | Раздельно | `Detector::detect(&str)` принимает только строку и не выражает составной вход «token + отпечаток + местоположение + время», поэтому `session` / `throttle` живут отдельно от `Scanner` |
| fail-closed vs fail-open | Аутентификация fail-closed, ограничение частоты fail-open | Пропустить вердикт сессии — значит обойти проверку, поэтому нужен блок; блокировать всех пользователей из-за ограничения — само-DoS, а основной барьер аутентификации всё ещё на месте, так что решение остаётся за вызывающей стороной |

### Два уровня: сильные и слабые сигналы

Детектор **не** сообщает о каждом совпадении с объявленной серьёзностью. 18 из 32 детекторов делят свои паттерны на два уровня (статические таблицы `STRONG_PATTERNS` / `WEAK_PATTERNS` в исходниках):

| Уровень | Критерий | Сообщаемая серьёзность | Одиночное совпадение пересекает порог отказа |
|------|------|-----------|------------------|
| **Сильный сигнал** | Сама форма может возникнуть только из атаки | Объявленный уровень детектора | Да |
| **Слабый сигнал** | Токен всего лишь «встречается» — в обычном содержимом он повсюду | Всегда `Severity::Low` (5 баллов) | **Нет** |

Оба уровня проходят через один и тот же детектор и один и тот же `attack_type`; различается только `severity`. Слабые сигналы **по-прежнему обнаруживаются** и не теряются молча: они видны в `scan()` и продолжают накапливаться в `assess()`.

Прямое следствие для вызывающей стороны: **одиночный слабый сигнал не является основанием для отказа.** Порог отказа эталонного конвейера ([`examples/waf.rs:166`](../../../examples/waf.rs)) — `risk.level >= RiskLevel::High` (40 баллов), а одиночный слабый сигнал стоит 5 баллов и в эту ветку не попадает. Чтобы разглядеть атаку за слабыми сигналами, смотрите на то, что даёт `assess()`, когда совпадения от нескольких детекторов складываются:

```rust
let scanner = Scanner::default();

// Три слабых сигнала от трёх разных детекторов — поднимает только сумма
let a = scanner.assess("<script src=\"/app.js\"></script>\n../config\n__proto__");
// a.results == 3, a.score == 15 (3 × Low) → RiskLevel::Medium
// всё ещё ниже High; любое дальнейшее совпадение в том же запросе перейдёт порог
```

В слабый уровень переведены токены, у которых «само появление — норма»:

| Слабый сигнал | Почему он не может отказать в одиночку |
|--------|-------------------|
| `<script src=...>`, `<iframe>`, `<link>`, `expression(` | Есть на каждой веб-странице |
| Одноуровневый `../` | Относительные пути в каждом исходнике |
| `-2`, `+1` в начале строки | Пункты списков Markdown, отрицательные числа в тексте |
| Голый `__proto__` (чтение прототипа) | Любой JS, трогающий цепочку прототипов |
| `${env:}` / `${sys:}` | Легальный синтаксис конфигурации log4j2 |
| `X-Forwarded-Host`, `X-Original-URL` | Обратный прокси добавляет их сам |
| `Host: 10.244.1.5`, `Host: localhost` | Вызовы pod-to-pod в k8s, локальная разработка |
| Голые `10.0.0.5`, `192.168.1.1`, `127.0.0.1` | `X-Forwarded-For`, `bind 127.0.0.1` |
| Протокол-относительный URL `//evil.com` | Комментарии в исходниках, ссылки на CDN в документации |
| `information_schema` | Логи ошибок PG, учебники по SQL |

Таблица выше — только пример. Критерий — **форма**, а не имя файла: для того же `../` один уровень (`../x`) слабый, а несколько уровней (`../../`) — сильный ([`src/file/path_traversal.rs`](../../../src/file/path_traversal.rs)). Полный список — в `WEAK_PATTERNS` каждого детектора и в пометке `слаб.` в таблицах ниже.

## Архитектура дизайна

<img src="../../diagrams/architecture.svg" alt="Архитектура security-rust: вызывающая сторона → слой обнаружения → слой оценки → слой защиты → хранилище" width="900">

Пять слоёв сверху вниз: **вызывающая сторона** (WAF / шлюз / аудит / CLI) → **слой обнаружения** (`Scanner` с `Vec<Box<dyn Detector>>`, 32 детектора в 4 категориях) → **слой оценки** (`score::assess`) → **слой защиты** (`SessionGuard` / `Throttle`, каждый привязан к своему trait хранилища) → **абстракция хранилища** (встроенный `MemoryStore`, Redis реализует вызывающая сторона).
*(Подписи на диаграммах — на китайском; метки — это имена API.)*

Trait `Detector` — единственный контракт слоя обнаружения: `fn detect(&self, input: &str) -> Option<DetectionResult>`. `session`, `throttle` и `score` его не реализуют — их вход не является одной строкой (token + отпечаток + местоположение + время), либо они потребляют результаты сканирования вместо сырого ввода, — поэтому они отвечают самостоятельно (см. ниже). Красная линия возврата справа отмечает границу библиотеки: **вердикт возвращается вызывающей стороне для исполнения**; сама библиотека никогда не касается запроса.

### Структура результата обнаружения

`DetectionResult` структурированно возвращает шесть полей: `attack_type`, `category`, `severity`, `matched_pattern`, `offset`, `message`. Полное определение см. в [Справочнике API](./API.md).

## Реализованные функции

<img src="../../diagrams/features.svg" alt="Функции security-rust: инъекции 11, протокол 11, данные 7, файлы 3, плюс три модуля с состоянием" width="900">

32 детектора собраны по четырём категориям и включены по умолчанию через `Scanner::default()` без всякой настройки; таблицы ниже перечисляют покрываемые каждым из них паттерны атак и серьёзность. Серьёзность описывает одно совпадение; агрегированный риск возвращает `Scanner::assess()`.

Помеченные `слаб.` паттерны в таблицах — это **слабые сигналы**: они сообщаются как `Severity::Low` (5 баллов) и не пересекают порог отказа в одиночку (подробнее в разделе выше). Столбец «Серьёзность» — это **потолок**, которого детектор может достичь; у детектора с пометкой `слаб.` есть оба уровня, и его сильные паттерны по-прежнему сообщаются с объявленным уровнем. У детектора, слабого целиком (`dns_rebinding`), потолок равен `Low`.
*(Подписи на диаграммах — на китайском; метки — это имена API.)*

### Инъекционные атаки (11 детекторов)

| Детектор | Покрываемые паттерны | Серьёзность |
|----------|----------------------|-------------|
| **xss** | Полная таблица обработчиков событий `onerror=`/`onload=` и др., псевдопротоколы `javascript:`/`vbscript:` (только scheme, за которым сразу идёт непробельный символ); `слаб.`: теги `<script src=...>`/`<iframe>`/`<embed>`/`<object>`/`<link>`, CSS `expression(` | Critical |
| **sql_injection** | `UNION SELECT`, инъекции с задержкой `sleep()`/`benchmark()`/`pg_sleep()` (только в позиции оператора), хранимые процедуры `exec sp_`/`xp_`, паттерны слепых boolean-инъекций `' OR '1'='1`, `LOAD_FILE()`/`INTO OUTFILE`, `DROP TABLE`/`INSERT INTO`, разрыв слова комментарием `UN/**/ION`; `слаб.`: само слово `information_schema` | Critical |
| **command_injection** | reverse shell `/dev/tcp`, формы вызова `passthru()`/`shell_exec()`/`system("…")`/`popen()`/`pcntl_exec()`, формы вызова `powershell -Command`/`cmd.exe /c`; `слаб.`: span в обратных кавычках, подкоманды `$()`, цепочки через pipe/`\|\|`/`&&`, `exec(`, `>/dev/null`, связка reader+путь вида `cat /etc/passwd`, голые слова `cmd.exe`/`powershell` | Critical |
| **nosql_injection** | Операторы MongoDB `$ne`/`$gt`/`$regex`/`$where`, инъекция `$or`, обход аутентификации `{"$gt": ""}` | Critical |
| **ldap_injection** | Операторы фильтров `(&` `(\|` `(!`, перечисление атрибутов `*(cn=`, инъекции `objectClass`/`uid` | High |
| **xpath_injection** | Обход boolean `' or '1'='1`, инъекция функции `' or true()`, обход узлов `'] \| '` | High |
| **jndi_injection** | сам lookup `${jndi:`, свёртка регистра `${lower:j}`/`${upper:j}`, свёртка пустой строкой `${::-j}` (существует только чтобы замаскировать `jndi`); `слаб.`: легальный синтаксис lookup `${env:}`/`${sys:}`/`${java:}` | Critical |
| **ssi_injection** | Выполнение команд `<!--#exec cmd=`, включение `<!--#include file=` с абсолютным путём или `..`, экспорт окружения `<!--#printenv`; `слаб.`: вывод переменных `<!--#echo var=`, информация о файлах `<!--#fsize`/`<!--#flastmod`, `<!--#config`, обычное включение вида `<!--#include file="header.html"` | High |
| **graphql_injection** | Интроспекционные запросы `__schema {`/`__type {` с набором выборки (упоминание имени поля в прозе не репортится); `слаб.`: `__typename` (Apollo/Relay добавляют его в каждый запрос), вложенность фигурных скобок ≥5 уровней | Medium |
| **ssti** | Jinja2 `{{ }}` / FreeMarker `${ }` — **вычисление внутри разделителей** (`{{7*7}}`, `${7*7}`, `{{config`, `${T(java.lang.Runtime)}`, `${@Type@method}`), шаблонный LFI через `{% include '/…'` / `..`, цепочки побега внутри разделителей `__mro__`/`__subclasses__()`/`__globals__`/`__builtins__`/`__class__`/`__dict__`, FreeMarker `?new(`; `слаб.`: голые шаблонные директивы `{% %}`, `<%=`/`<%@`, `#set(`, голые магические атрибуты; сами разделители сигналом не являются, простой плейсхолдер вида `${x}` не репортится | Critical |
| **format_string** | спецификаторы записи `%n` (в том числе с модификаторами длины), завышенная ширина `%123456d`, повторяющиеся спецификаторы `%x`/`%p`/`%s` (утечка форматной строки / повреждение памяти) | Medium |

### Протокольные атаки и атаки на запросы (11 детекторов)

| Детектор | Покрываемые паттерны | Серьёзность |
|----------|----------------------|-------------|
| **ssrf** | Облачные метаданные `169.254.169.254` и `metadata.google.internal` (контекст URL не требуется), внутренние IP в позиции **URL authority** (после `//`): `10.x`/`172.16-31.x`/`192.168.x`/`127.x`, `//localhost`, `//0.0.0.0`, `//[::1]`, опасные протоколы `gopher://`/`dict://`/`ftp://user@`/`file:///`; `слаб.`: те же внутренние литералы **вне позиции URL** (`X-Forwarded-For: 10.0.0.5`, `bind 127.0.0.1`, `{"host": "10.0.0.1"}` — байт в байт) | Critical |

## Известные ограничения

Ниже — **известные и намеренно сохранённые** границы, а не ждущие исправления дефекты. Прежде чем что-то менять, прочтите обоснование: каждая граница получена измерением, и каждую уже пробовали затянуть — и упирались в ту же стену.

### `dns_rebinding` только сообщает, но не блокирует

Его критерий — «в `Host:` появляется внутренний адрес», а та же форма — это и каждый вызов pod-to-pod в k8s (`Host: 10.244.1.5:8080`), и каждая локальная разработка (`Host: localhost:8000`), и каждый запрос в сети Docker-контейнера (`172.18.0.2`). Настоящий rebinding — это «публичное доменное имя + результат разрешения, указывающий внутрь», а `Host`, который отправляет браузер, — как раз это публичное имя: **в одной строке нет истории разрешения**, поэтому форма, которую проверяет детектор, не совпадает с формой атаки. Затянуть её нельзя: какую бы проверку ни добавить, она останется «появился внутренний адрес». Поэтому весь детектор слабый, всегда `Low`, и сколько бы совпадений ни сложилось, сам он порог отказа не пересечёт. Защита — сравнение IP **после** разрешения, а не на строковом уровне.

### Эта библиотека не может сканировать собственные исходники, тесты и документацию

Потолок сигнатурного сканера: измерено, что в этом репозитории 78 файлов из 298 пересекают порог отказа, и все они содержат атакующие строки **по построению** — тестовые полезные нагрузки, собственные литералы регулярных выражений в исходниках детекторов, а также README и таблицы OWASP, где эти паттерны перечислены. README не становится дефектом оттого, что в нём написан `(a+)+`. Чтобы просканировать собственные артефакты, этот корпус придётся сначала исключить — или взять другой критерий.

### `upload` сообщает `<%@` / `<?php` как Critical всегда

Контракт этого детектора — «**этот blob есть серверный исполняемый код**»: появление уже достаточно, поэтому уровни здесь не вводятся. Преамбула JSP-страницы и JSP-webshell совпадает байт в байт (`<%@ page language="java" … %>` и `<%@ page import="java.io.*" %>` — одна и та же форма), а перевод `<%@`/`<%=` на слабый уровень опустил бы webshell ниже порога отказа — то есть удалил бы детектор под другим названием. Цена: сканирование страницы, **которая сейчас отдаётся клиентам** (а не загружаемого файла), тоже даёт совпадение — это несовпадение области входа, и сообщение о совпадении `Malicious file upload detected` эту область называет.

### `path_traversal` сообщает `(?:\.\./){2,}` как Critical

Глубокие относительные пути в монорепозитории (`from '../../../shared/domain'`) дают совпадение. Дальше не затянуто, потому что единственное ограничение, отделяющее это от атаки, — список имён целевых файлов (`../etc/passwd` и подобные), а он покрывает только системные файлы: атакующий просто выберет другую цель для LFI.

## Модули с состоянием

`session`, `throttle` и `score` — **не** реализации `Detector`. `session` и `throttle` хранят состояние и привязаны к идентичности: `Detector::detect(&self, input: &str)` не способен выразить составной вход из токена, отпечатка, местоположения и времени. Поэтому они стоят рядом с цепочкой детекторов, а не внутри неё.

| Модуль | Тип | Назначение |
|------|------|------|
| `session` | `SessionGuard<S: SessionStore>` | Безопасность сессий: перехват клиента, подмена данных, вход из необычного места, токен-сессии. Методы `bind`/`verify`/`revoke`/`revoke_all`/`rotate`; `Decision { Allow, Challenge, Block }` + `SessionThreat`; `SessionConfig` (`ttl_secs` 3600, `impossible_travel_kmh` 900.0, `timestamp_skew_secs` 300); трейт `SessionStore` + `MemoryStore` |
| `throttle` | `Throttle<S: ThrottleStore>` | Ограничение частоты и бан: скользящее окно, бан по порогу, блокировка учётной записи. Методы `check`/`check_any`/`record_failure`/`record_success`/`reset`/`purge_expired`; `ThrottleDecision { Allow { remaining }, Banned { until }, Unavailable }`; `ThrottleConfig` (`threshold` 5, `window_secs` 60, `ban_secs` 900); `record_failure` возвращает `ThrottleOutcome` (`Allow`/`Banned`), без `Unavailable` |
| `score` | `RiskLevel`, `RiskAssessment`, `Scanner::assess()` | Оценка риска: агрегирует отдельные сигналы низкой серьёзности в измеримую величину. `RiskLevel { None, Low, Medium, High, Critical }` |

**Асимметрия при сбоях намеренна.** При отказе хранилища `SessionGuard` возвращает `Decision::Block` (`StoreUnavailable`) — fail-closed, запрос никогда не пропускается. `Throttle` — сознательное исключение: ограничение частоты относится к эшелонированной защите, а не к основному барьеру аутентификации, поэтому сбой бэкенда возвращает `ThrottleDecision::Unavailable`, а не `Banned` — заблокировать всех пользователей было бы само-DoS. Решение остаётся за вызывающей стороной.

**Новых зависимостей по-прежнему нет:** в списке только `regex`. Плата за это: токен и подпись предоставляет вызывающая сторона, позиции она же и разбирает. Оба модуля абстрагируют хранилище трейтом — для развёртывания в несколько экземпляров достаточно реализовать `SessionStore`/`ThrottleStore` поверх Redis.

## Жизненный цикл

<img src="../../diagrams/lifecycle.svg" alt="Три жизненных цикла security-rust: сканирование, сессия, ограничение частоты" width="900">

Три жизненных цикла независимы друг от друга; единственная точка их пересечения — функция обработки запроса на стороне вызывающей стороны:

| Жизненный цикл | Начало | Конец | Где хранится состояние |
|-----------|-----------|---------|----------------|
| **Сканирование** | `Scanner::scan(&str)` | `Vec<DetectionResult>` → `score::assess` → `RiskAssessment` | Нет — без состояния, каждый вызов независим |
| **Сессия** | `SessionGuard::bind()` пишет `SessionRecord` | `verify()` на каждый запрос → `SessionVerdict` ⇒ `Allow` / `Challenge` / `Block` | `SessionStore` (встроенный `MemoryStore`) |
| **Ограничение частоты** | `Throttle::check_any(&[keys])` | `Allow{remaining}` / `Banned{until}` / `Unavailable` | `ThrottleStore` (встроенный `MemoryThrottleStore`) |

Две границы, на которых легко ошибиться:

- **`remaining == 0` означает, что запрос следует отклонить** —— квота исчерпана, а не «осталась ещё одна попытка». Не перепутайте при записи заголовков `X-RateLimit-*`.
- **Сбои хранилища обрабатываются в противоположных направлениях**: `SessionGuard` — fail-closed (`StoreUnavailable` ⇒ `Block`, никогда не пропускать, иначе атакующий, вызвав сбой, подменит целый класс проверок); `Throttle` — fail-open (`Unavailable` передаётся вызывающей стороне: блокировать всех пользователей при сбое бэкенда — это само-DoS, а основной барьер `SessionGuard` всё ещё блокирует). Это зафиксированное проектное решение, а не забытый fallback.

## Использование

Готово к использованию без настройки:

```rust
use security_rust::Scanner;

let scanner = Scanner::default();

// Сильный сигнал: сама форма может возникнуть только из атаки ⇒ сообщается с объявленной серьёзностью
let results = scanner.scan("<img src=x onerror=alert(1)>");
// [CRITICAL] XSS cross-site scripting detected — offset: 11, pattern: onerror=

// Слабый сигнал: токен всего лишь встречается ⇒ всегда Low, порог отказа в одиночку не пересекает (см. «Два уровня»)
let weak = scanner.scan("<script src=\"/app.js\"></script>");
// [LOW] XSS tag present (weak signal) — offset: 0, pattern: <script>
```

Оценка риска сводит список совпадений к одному уровню, чтобы несколько сигналов низкой серьёзности не были молча проигнорированы:

```rust
let assessment = scanner.assess("=cmd|' /C calc'!A0 `cat /etc/passwd` ../../../etc/passwd");
// assessment.level   >= RiskLevel::High
// assessment.results >= 3
// assessment.score   — сырые взвешенные баллы
```

Полный справочник API (установка, выборочное сканирование, пользовательская настройка, оценка риска, отображение серьёзности, безопасность сессий, ограничение частоты и баны, производительность) см. в [Справочнике API](./API.md).

### Безопасность сессий (`session`)

```rust
use security_rust::session::{Decision, MemoryStore, RequestContext, SessionConfig, SessionGuard};

let guard = SessionGuard::new(MemoryStore::new(), SessionConfig::default());

let login = RequestContext {
    token: "tok-abc",
    subject: "u-1",
    fingerprint: "ip=1.2.3.4|ua=curl",   // отпечаток клиента, привязывается при входе
    location: Some("CN-BJ"),
    coords: Some((39.9042, 116.4074)),
    signature: None,                      // MAC подписывает вызывающая сторона
    at: None,
};

// Вход: создать сессию + привязать отпечаток + записать местоположение; другое место влияет только на verdict, вход не блокируется
guard.bind(&login, 1_700_000_000).unwrap();

// Проверка на каждый запрос: тот же token с другим отпечатком ⇒ перехват клиента
let verdict = guard.verify(&RequestContext { fingerprint: "ip=5.6.7.8|ua=curl", ..login }, 1_700_000_010);

match verdict.decision {
    Decision::Allow => { /* пропустить */ }
    Decision::Challenge => { /* пропустить, но потребовать вторую проверку: другое место, расхождение часов, неожиданная подпись */ }
    Decision::Block => { /* отклонить */ }
}
```

### Ограничение частоты и баны (`throttle`)

```rust
use security_rust::throttle::{MemoryThrottleStore, Throttle, ThrottleConfig, ThrottleDecision};

let throttle = Throttle::new(MemoryThrottleStore::new(), ThrottleConfig::default());
let key = "acct:u-1"; // key строит и нормализует вызывающая сторона; не передавайте сырой ввод как key
let now = 1_700_000_000;

// У реального запроса два измерения: IP и аккаунт. check_any опрашивает оба сразу и объединяет по строгости
match throttle.check_any(&["ip:1.2.3.4", key], now) {
    // remaining можно отдать в X-RateLimit-*; **remaining == 0 означает, что запрос надо отклонить**
    ThrottleDecision::Allow { remaining } => { /* остаток квоты remaining */ }
    // now >= until — бан снят
    ThrottleDecision::Banned { until } => { /* бан действует до until */ }
    // Сбой бэкенда: модуль не решает за вызывающую сторону (рекомендуется пропустить + оповестить)
    ThrottleDecision::Unavailable => { /* бэкенд ограничения недоступен */ }
}

// Записать неудачную аутентификацию: при достижении threshold — бан. Возвращается ThrottleOutcome (два состояния),
// сбой хранилища идёт в Err —— не нужно писать код ради ветки Unavailable, которая никогда не выполнится
let _ = throttle.record_failure(key, now);
```
